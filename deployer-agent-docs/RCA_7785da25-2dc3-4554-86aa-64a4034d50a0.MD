# RCA — Stripe webhook failing at https://myatelierapp.it/api/stripe/webhook

## Problem statement
Stripe reports the webhook endpoint `POST https://myatelierapp.it/api/stripe/webhook` failing since 22 Oct 2026 (34 attempts, auto-disable 31 Oct). Asked to (1) confirm the actual status code/error returned to Stripe, (2) confirm the two Stripe secrets exist in prod, (3) confirm the route is reachable.

## Environment
- Deployment: virtual-try-on-334, active run `7785da25-2dc3-4554-86aa-64a4034d50a0` (status success, app is LIVE).
- Frontend type: cloudflare (so `/api/*` reaches the k8s backend via the Cloudflare worker proxy).

## Findings

### 1) What Stripe actually receives: HTTP 400 (our own "invalid signature" path) — NOT 404 / 5xx / timeout / redirect
Production backend access logs (last 24h) show every webhook delivery hitting the route and being rejected with 400:
```
INFO: 104.23.245.126 - "POST /api/stripe/webhook HTTP/1.1" 400 Bad Request ×2
INFO: 162.159.114.57 - "POST /api/stripe/webhook HTTP/1.1" 400 Bad Request
INFO: 104.23.243.9  - "POST /api/stripe/webhook HTTP/1.1" 400 Bad Request
...
```
(Source IPs are Cloudflare edge — the worker proxy is correctly forwarding Stripe's POST to the backend.) Log scorecard: 8 app-level ERRORs, status_counts {400: 8}. No 404, no 5xx, no redirect.

The app error lines show signature verification is the cause:
```
server - ERROR - stripe webhook: signature verification failed
  (SignatureVerificationError: No signatures found matching the expected signature for payload)
  — check STRIPE_LIVE_WEBHOOK_SECRET matches the endpoint signing secret   (×6, Oct 27)
server - ERROR - stripe webhook: signature verification failed
  (SignatureVerificationError: Unable to extract timestamp and signatures from header)  (×2, Oct 28)
```
The dominant error — "No signatures found matching the expected signature for payload" — means the `Stripe-Signature` header WAS present and parsed (timestamp + v1 signatures extracted), but the HMAC computed with the stored `STRIPE_LIVE_WEBHOOK_SECRET` does not match. That is a signing-secret mismatch, i.e. the value stored in prod is not the signing secret of this live Stripe endpoint.

### 2) Secrets exist in production
`list_secrets` on the active run confirms both keys are present and non-blank:
- `STRIPE_LIVE_WEBHOOK_SECRET` — present, is_empty=false
- `STRIPE_LIVE_SECRET_KEY` — present, is_empty=false
(Also present: STRIPE_LIVE_PUBLISHABLE_KEY.)

HOWEVER — values are present but appear to be the WRONG kind. The app's own startup log says:
```
Stripe: LIVE keys missing (or test keys set) — checkout is disabled until
STRIPE_LIVE_SECRET_KEY/STRIPE_LIVE_PUBLISHABLE_KEY live are set
```
This fires even though the secrets are non-empty, so the stored Stripe values are not recognized as live keys (likely `sk_test_…` / test-mode values, or otherwise not the live-endpoint values). Note: secret VALUES are never exposed to me, so the exact value is UNVERIFIED — but the combination of (a) startup "test keys set" warning and (b) persistent HMAC mismatch points to the stored Stripe values not matching the live Stripe configuration.

### 3) Route is reachable — confirmed
Live probe of `GET /api/stripe/webhook` on the production URL returned:
```
405 Method Not Allowed  body={"detail":"Method Not Allowed"}  content-type application/json
```
A 405 from FastAPI proves the route exists and the request reaches the backend (a POST-only route correctly rejects GET). It is NOT a 404, NOT a 502, NOT a redirect. Combined with the POST-side logs returning our app's 400, the path/proxy/routing are all healthy.

## Root cause
The webhook endpoint, proxy and backend are all working correctly. Stripe deliveries reach the backend and are rejected with our own HTTP 400 because `stripe.Webhook.construct_event` signature verification fails — the `STRIPE_LIVE_WEBHOOK_SECRET` stored in production does not match the signing secret of the live Stripe webhook endpoint for `https://myatelierapp.it/api/stripe/webhook`. The parallel startup warning that live Stripe keys are "missing (or test keys set)" indicates the stored `STRIPE_LIVE_SECRET_KEY`/publishable values are likely test-mode values too — i.e. the Stripe secret set in prod is from the wrong account/mode or a stale endpoint.

This is a secret-value problem, owned by the user via the Secrets tab. It is not a code, routing, proxy, or infra fault, and not something I can fix (secret values are not settable or readable by me).

## Suggested fix (user)
In Stripe Dashboard (live mode) open the webhook endpoint for `https://myatelierapp.it/api/stripe/webhook`, copy its **Signing secret** (`whsec_…`), and set `STRIPE_LIVE_WEBHOOK_SECRET` to that exact value in Deployment Panel → Secrets. Also set `STRIPE_LIVE_SECRET_KEY` (and `STRIPE_LIVE_PUBLISHABLE_KEY`) to the LIVE keys (`sk_live_…` / `pk_live_…`), since the app currently reports them as missing/test. Then redeploy to apply. After redeploy, use Stripe's "Send test webhook" / resend a failed event to confirm a 200. (Do before 31 Oct to avoid auto-disable.)

No deploy, redeploy, or secret change was performed during this investigation.
