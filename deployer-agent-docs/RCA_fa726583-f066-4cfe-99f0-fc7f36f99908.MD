# RCA — Stripe webhook deliveries failing on myatelierapp.it

Deployment: virtual-try-on-334 (816103ce-...) — active run fa726583-f066-4cfe-99f0-fc7f36f99908
Frontend: cloudflare | Live URL: https://virtual-try-on-334.emergent.host
Symptom: Stripe webhook https://myatelierapp.it/api/stripe/webhook returns failed deliveries ("Non riuscito"), e.g. checkout.session.expired at 25 Oct 18:12:46.

## (1) Stripe secrets present in PRODUCTION (active run)
All present and non-empty:
- STRIPE_ACCOUNT_ID
- STRIPE_MODE
- STRIPE_PUBLISHABLE_KEY
- STRIPE_SECRET_KEY
- STRIPE_WEBHOOK_SECRET

Values are never returned. Prefix / mode verdict (no values revealed):
- STRIPE_MODE = "test" — CONFIRMED via list_secrets equals (matches_expected:true for "test", false for "live").
- STRIPE_SECRET_KEY / STRIPE_PUBLISHABLE_KEY are NOT live-prefixed. The app's own startup guard logged:
  `Stripe: LIVE keys missing (or test keys set) — checkout is disabled until STRIPE_SECRET_KEY/STRIPE_PUBLISHABLE_KEY live are set`
  This is the backend evaluating its own env and concluding the keys are not sk_live_/pk_live_. (The exact-value `equals` probe cannot test a prefix, so the backend guard log is the authoritative evidence.)

## (2) Production backend webhook failure reason — 400 signature, NOT 5xx
From active-run logs (loki):
- `2026-10-25 17:12:46 - server - ERROR - stripe webhook: signature verification failed (SignatureVerificationError: No signatures found matching the expected signature for payload) — check STRIPE_WEBHOOK_SECRET matches the endpoint signing secret`
- `2026-10-25 17:31:22 - server - ERROR - stripe webhook: signature verification failed (SignatureVerificationError ...)`
- `POST /api/stripe/webhook HTTP/1.1" 400 Bad Request` (x2)

So the endpoint returns **400 on signature mismatch** (construct_event raises SignatureVerificationError), not a 5xx. No crash/5xx involved.

## (3) Are the production Stripe secrets platform-managed or user-editable?
STRIPE_* are platform SYSTEM keys. Per the platform secrets model they are regenerated from production state on EVERY deploy and always overwrite any preview/user value. Production is therefore running the Emergent-managed Stripe SANDBOX account (acct_1UU2OmA3yegZw5Gp, lifecycle_state=unclaimed, STRIPE_MODE=test) — NOT the user's own live Stripe account.

## Why the webhook fails (both facts tie together)
The user registered the webhook endpoint on their OWN live Stripe account. Production verifies the signature with the Emergent sandbox STRIPE_WEBHOOK_SECRET (different account). The signing secrets don't match → "No signatures found matching the expected signature" → 400 → Stripe marks the delivery "Non riuscito". Separately, because the live-key guard fails, checkout itself is disabled (503) in production.

## Fix
Because STRIPE_* are platform-managed and overwritten each deploy, pasting live keys into the Secrets tab will NOT stick. To go live the user must claim/activate their own Stripe through Emergent's managed Stripe integration (the sandbox account is currently "unclaimed"), so production is provisioned with the user's live STRIPE_SECRET_KEY/STRIPE_PUBLISHABLE_KEY AND the matching live STRIPE_WEBHOOK_SECRET for the endpoint they registered. This typically requires the Emergent Stripe connect/claim flow and/or Emergent support. No code or manifest change is involved.

No deploy or secret modification was performed.
